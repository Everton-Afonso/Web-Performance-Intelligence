1. Visão geral do produto

O Performance Auditor será uma ferramenta de auditoria técnica para desenvolvedores, equipes de
e-commerce, agências e clientes. O usuário informa uma URL e escolhe o dispositivo de análise. O
sistema executa uma auditoria, apresenta as principais métricas de performance, identifica
oportunidades de melhoria e, na evolução completa, explica o porquê dos problemas, o que deve ser
corrigido primeiro, como corrigir e se a correção realmente melhorou a performance.

   Princípio do produto: não ser apenas um clone do PageSpeed Insights.

A proposta final é transformar dados técnicos em um plano de ação: "Meu site está ruim. Por quê? O
que devo corrigir primeiro? Como corrijo? E a correção realmente melhorou a performance?"

1.1 Fontes de dados e motores

· Google PageSpeed Insights / Lighthouse: auditoria de laboratório.
· CrUX: dados reais de usuários, previstos a partir da V2.
· Análise de código: contextualização de causas e sugestões, especialmente na camada de IA.
· Performance Engine: normalização, classificação, scoring, priorização e comparação.
· IA/LLM: interpretação, causa provável, recomendações e exemplos de implementação.

2. Métricas e critérios de performance

A V1 deve trabalhar com as métricas disponíveis no resultado do Lighthouse/PageSpeed.

Métrica  Bom                                  Precisa melhorar                         Ruim

LCP       2,5 s                               2,5-4 s                                  > 4 s

INP       200 ms                              200-500 ms                               > 500 ms

CLS       0,1                                 0,1-0,25                                 > 0,25

Também devem ser apresentadas quando disponíveis: FCP, TTFB, Speed Index, Total Blocking Time,
tamanho da página, quantidade de requests e indicadores relacionados a JavaScript, CSS e imagens.

Nota: os limites e integrações externas devem ser revisados conforme as versões atuais das APIs e
das definições oficiais de Core Web Vitals antes da produção.

5. Arquitetura completa planejada

backend concentra validação, integrações externas, normalização e regras de negócio.

Frontend        React + Vite + TypeScript; formulário, loading, cards de métricas, dashboard, histórico, gráficos e resultados.
Backend         Node.js + TypeScript + Express; API REST, validação, integração, normalização e regras de negócio.
Performance     Google PageSpeed Insights API / Lighthouse.
Dados de campo  CrUX API, previsto para V2.
Persistência    PostgreSQL + Prisma, previsto para V2.
IA              LLM para interpretação e geração de recomendações, previsto para V3.
Relatórios      HTML/PDF, evoluindo de relatório técnico para relatório executivo + técnico.
Produção        Docker, variáveis de ambiente, segurança, rate limiting, logs, testes, CI/CD e deploy.

Atualização da especificação -- WebPageTest API

Versão do documento: 1.1 · Setembro de 2026
Esta seção complementa o documento consolidado original, adicionando o WebPageTest como motor de análise técnica
avançada e atualizando arquitetura, fluxo, modelo de dados e roadmap.

1. WebPageTest API

O WebPageTest será uma fonte complementar de análise profunda. O PageSpeed Insights/Lighthouse permanece como o
principal motor de auditoria de laboratório, enquanto o CrUX representa dados de experiência de usuários reais. O
WebPageTest acrescenta uma visão detalhada do carregamento da página, waterfall, requests, recursos e métricas do teste.

1.1 Papel no produto

A integração deverá ser usada para responder perguntas que exigem evidência técnica mais detalhada, por exemplo: quais
requests estão consumindo mais tempo, quais recursos estão aumentando o peso da página, quais terceiros participam do
carregamento e onde está o gargalo observado no waterfall.

1.2 Capacidades planejadas

· Executar testes automatizados de uma URL a partir do backend.
· Coletar métricas de carregamento e desempenho retornadas pelo teste.
· Analisar waterfall e requests individuais.
· Identificar volume transferido e distribuição dos recursos.
· Agrupar recursos por JavaScript, CSS, imagens, fontes e terceiros.
· Complementar a análise de Core Web Vitals quando os dados estiverem disponíveis.
· Registrar o identificador do teste e o timestamp para histórico e comparação.
· Usar WebPageTest como investigação avançada quando PageSpeed/Lighthouse detectar problemas relevantes.

1.3 Importante sobre acesso e custo

O WebPageTest possui um plano Starter gratuito para execução de testes no site, mas a documentação oficial informa que a
WebPageTest API é um recurso do plano Pro. Portanto, a automação por API não deve ser tratada no projeto como uma API
gratuita e ilimitada. A aplicação deve encapsular a integração, controlar quota/uso e permitir que a funcionalidade seja habilitada
somente quando houver uma chave válida.
Para o volume planejado de aproximadamente 20-30 URLs por dia, a integração continua tecnicamente viável, mas deve
considerar a quantidade de test runs, principalmente se forem executadas múltiplas cargas por URL ou testes Mobile/Desktop.

1.4 Dados que interessam ao Performance Auditor

· Métricas de carregamento e desempenho do teste.
· Core Web Vitals disponíveis no resultado.
· Waterfall e evidências por request.
· Quantidade de requests e bytes transferidos.
· Distribuição dos recursos por tipo.
· Informações de terceiros e domínios envolvidos no carregamento.
· Dados CrUX disponibilizados pelo WebPageTest quando presentes.
· Referência do teste, status e data/hora.

2. Integração arquitetural

laboratório do Lighthouse, uma métrica de campo do CrUX e uma métrica técnica do WebPageTest.

5. Estratégia de execução

O WebPageTest não precisa obrigatoriamente ser executado em todas as análises. Para reduzir tempo, consumo e
dependência externa, o Performance Auditor pode adotar uma estratégia em duas etapas:
· Etapa 1 -- PageSpeed/Lighthouse + CrUX: coleta inicial e classificação.
· Etapa 2 -- WebPageTest: executado quando solicitado pelo usuário ou quando regras de severidade indicarem necessidade
de diagnóstico profundo.

Exemplos de gatilhos para análise avançada:

· LCP ou TTFB acima do limite definido.
· Grande quantidade de requests.
· Peso elevado de JavaScript, CSS, imagens ou fontes.
· Problemas relevantes de renderização ou carregamento identificados pelo Lighthouse.
· Necessidade de waterfall para investigar a causa de um problema.
· Comparação antes/depois em uma otimização importante.

8. Referência oficial utilizada

A documentação oficial do WebPageTest informa que o Starter é gratuito para testes e que a WebPageTest API faz parte do
plano Pro. Também informa que a API fornece métricas de Core Web Vitals e pode incluir dados específicos de URL do CrUX
nos resultados. Essas condições devem ser revalidadas antes da produção, pois planos e limites podem mudar.

Nota: esta atualização corrige a interpretação de que a WebPageTest API seria necessariamente gratuita. O uso gratuito do WebPageTest não implica
acesso gratuito e ilimitado à API.
